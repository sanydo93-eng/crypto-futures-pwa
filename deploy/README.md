# Доступ к серверу 5.10.218.52:8100 с телефона

## Что проверено

Из моей песочницы `http://5.10.218.52:8100/` **недоступен**, но это ничего не
доказывает: исходящий трафик здесь идёт через прокси с белым списком хостов.

- порт 8100 заблокирован политикой egress самой песочницы;
- порты 80/443 отвечают `403 host_not_allowed` от прокси, а не от твоего сервера
  (проверено контрольным запросом на заведомо несуществующий адрес — ответ такой же).

Вывод: **проверить сервер снаружи я не могу**, диагностику надо запускать на самом
сервере — для этого есть `deploy/diagnose.sh`.

```bash
bash deploy/diagnose.sh
```

Скрипт скажет, какой из трёх разделов ниже твой.

---

## A. Приложение слушает только 127.0.0.1

Самая частая причина. Признак: в выводе `ss -tlnp` видно `127.0.0.1:8100`.
Тогда сайт открывается на самом сервере, но снаружи — никогда.

Что менять, в зависимости от стека:

| Стек | Было | Стало |
|---|---|---|
| Vite (`vite.config.js`) | — | `server: { host: '0.0.0.0', port: 8100 }` |
| Vite (CLI) | `vite --port 8100` | `vite --host 0.0.0.0 --port 8100` |
| Next.js | `next start -p 8100` | `next start -H 0.0.0.0 -p 8100` |
| Node/Express | `app.listen(8100)` | `app.listen(8100, '0.0.0.0')` |
| Python http.server | `python -m http.server 8100` | `python -m http.server 8100 --bind 0.0.0.0` |
| Docker | `-p 127.0.0.1:8100:8100` | `-p 8100:8100` |

Для Vite ещё нужно разрешить внешний хост, иначе он ответит «Blocked request»:

```js
// vite.config.js
export default {
  server: {
    host: '0.0.0.0',
    port: 8100,
    allowedHosts: ['5.10.218.52', 'example.com'],
  },
}
```

> Dev-сервер (`vite dev`) — не для постоянного доступа снаружи. Для боевого
> использования собирай (`npm run build`) и раздавай статику через Caddy/nginx.

## B. Слушает 0.0.0.0, но снаружи не отвечает — firewall

Открыть порт локально:

```bash
sudo ufw allow 8100/tcp && sudo ufw reload     # ufw
sudo firewall-cmd --add-port=8100/tcp --permanent && sudo firewall-cmd --reload  # firewalld
```

Отдельно проверь **firewall/security group в панели хостера** — он выше уровнем,
чем ufw, и часто пропускает только 22/80/443. Порт 8100 там нужно открыть руками.

## C. Снаружи отвечает, но телефон не открывает — это HTTPS

Для PWA это ключевой пункт. По `http://` на голый IP на телефоне:

- **service worker не регистрируется** (нужен secure context) — офлайн, кэш,
  пуши не работают;
- **приложение не устанавливается** на домашний экран — Chrome не показывает
  баннер установки;
- Chrome Android с включённым «Always use secure connections» молча апгрейдит
  запрос до `https://5.10.218.52:8100`, где ничего не слушает → таймаут;
- некоторые мобильные операторы режут нестандартные порты, а IPv6-only сети с
  NAT64 не всегда пускают на голый IPv4-литерал.

Правильное решение — **домен + HTTPS**, приложение остаётся на 8100 за прокси:

1. Заведи домен (или бесплатный поддомен: DuckDNS, sslip.io) и поставь A-запись
   на `5.10.218.52`.
2. Открой 80 и 443 на сервере и в панели хостера.
3. Поставь Caddy и подложи `deploy/Caddyfile` (заменив `example.com` на свой
   домен) — сертификат Let's Encrypt он получит и продлит сам.
4. Открывай на телефоне `https://твой-домен/`.

### Быстрая временная проверка без домена

Если надо убедиться прямо сейчас, что дело именно в HTTPS/сети, а не в
приложении, — прокинь туннель с сервера:

```bash
# на сервере
ssh -R 80:localhost:8100 nokey@localhost.run
# или
cloudflared tunnel --url http://localhost:8100
```

Обе команды выдадут временный `https://…` адрес. Открылся с телефона —
значит приложение живо, и остаётся сделать постоянный HTTPS по шагам выше.
