# Теннис: сигналы на точный счёт

PWA, которая считает распределение по точному счёту теннисного матча и сравнивает
его с коэффициентами букмекера. Расхождение больше порога показывается как сигнал.

Зависимостей нет — только Node.js 20+. Ни сборки, ни `npm install`.

```bash
npm start                 # http://localhost:8100 на демо-данных
npm test                  # 39 тестов модели и расчёта преимущества
```

## Как это работает

Точный счёт не берётся из API — он выводится из модели, и это ключевая идея.
Дешёвые API коэффициентов рынок correct score вообще не отдают, а очки в теннисе
близки к независимым, что делает точный расчёт возможным.

```
статистика игроков          коэффициенты
   (spw / rpw)                букмекера
        │                         │
        ▼                         │
 вероятность выиграть            │
   очко на подаче                │
        │                         │
        ▼                         ▼
  цепь Маркова          снятие маржи (девиг)
  гейм → сет → матч              │
        │                         │
        └────────► сравнение ◄────┘
                       │
                  преимущество,
                  ставка по Келли
```

1. **Подача.** Для пары игроков считается `p` — вероятность выиграть очко на своей
   подаче. Аддитивная модель Klaassen & Magnus: сила подачи одного и сила приёма
   другого складываются как отклонения от среднего по туру с учётом покрытия.
2. **Гейм.** Замкнутая формула через сумму по счетам плюс розыгрыш «ровно».
3. **Тай-брейк.** Перебор по состояниям с точным учётом порядка подачи (период 4).
4. **Сет.** Динамическое программирование по счёту в геймах — на выходе полное
   распределение: 6-0, 6-1, … 7-6 и зеркальные.
5. **Матч.** Свёртка сетов с точным учётом того, кто подаёт первым в каждом
   следующем сете.
6. **Сравнение.** С котировок снимается маржа, дальше считается преимущество
   `p × кэф − 1` и доля банка по Келли.

Пространство состояний в теннисе крошечное, поэтому всё считается перебором
точно — Монте-Карло не нужно, результат детерминирован.

### Что модель показывает наглядно

Счета, где фаворит закрывает сет на своей подаче, заметно вероятнее соседних.
Для игрока с `p = 0.685` против `p = 0.59`:

| счёт 1-го сета | вероятность | кто подаёт последний гейм |
|---|---|---|
| 6-3 | 29.7% | фаворит держит подачу |
| 6-2 | 9.2% | нужен брейк |
| 6-1 | 11.1% | фаворит держит подачу |
| 6-4 | 8.9% | нужен брейк |

Пилообразность — не артефакт, а следствие правил. Модели, которые считают счёт
«на глазок» от вероятности победы, этот эффект теряют целиком.

## Данные

### Статистика игроков

Провайдеры коэффициентов проценты выигранных очков на подаче обычно не отдают,
поэтому справочник собирается отдельно из открытого архива Джеффа Сакманна:

```bash
node scripts/build-stats.js --from 2021 --to 2025
```

Скрипт скачает матчи ATP и WTA, посчитает по каждому игроку долю выигранных очков
на подаче и на приёме в разрезе покрытий и выведет актуальные базовые уровни тура —
перенеси их в `src/model/serve.js`.

У игроков с малой выборкой оценка автоматически стягивается к среднему по туру
(`shrink` в `src/stats.js`): наблюдаемые 72% подачи по пяти матчам — это шум,
и без усадки модель уверенно выдаёт мусорные сигналы.

### Коэффициенты

```bash
cp .env.example .env       # вписать API_TENNIS_KEY
PROVIDER=api-tennis npm start
```

**Схему ответа api-tennis нужно проверить перед боевым использованием.** Разбор в
`src/providers/apiTennis.js` написан по документации, но на живом ключе я его
проверить не мог — ключа у меня нет. Названия рынков у провайдера меняются.
Проверка занимает минуту:

```bash
API_TENNIS_KEY=... npm run probe
```

Скрипт покажет, что пришло и во что превратилось. Если рынков нет — поправь
карту `MARKET_ALIASES`. Молча разъехавшийся маппинг даст сигналы на пустом месте,
поэтому этот шаг пропускать нельзя.

Дешёвые API коэффициентов (The Odds API и аналоги) точный счёт не отдают — там
только победитель, фора и тотал. Рынок correct score есть у BetsAPI и у
провайдеров enterprise-уровня.

## Настройки

Всё через переменные окружения, см. `.env.example`:

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `PORT` / `HOST` | `8100` / `0.0.0.0` | `0.0.0.0` обязателен для доступа с телефона |
| `PROVIDER` | `mock` | `mock` или `api-tennis` |
| `MIN_EDGE` | `0.05` | Порог преимущества для сигнала |
| `MIN_PROBABILITY` | `0.02` | Отсечка редких исходов |
| `DEVIG_METHOD` | `power` | Способ снятия маржи |
| `KELLY_FRACTION` | `0.25` | Доля от полного критерия Келли |
| `CACHE_TTL_MS` | `120000` | Как часто ходить к провайдеру |

Про `DEVIG_METHOD`: `power` подбирает показатель `k` в `p = (1/кэф)^k`, что учитывает
переоценку аутсайдеров. На точном счёте с десятком исходов это заметно точнее
пропорционального деления, которое размазывает маржу поровну и завышает шансы
длинных исходов.

## Трезво про ожидания

Маржа на точном счёте — 15–25% против 2–5% на победителе матча. Это значит:

- модель должна быть **откалибрована**, а не просто «часто угадывать». Плохо
  откалиброванная модель на этом рынке уверенно проигрывает;
- базовые уровни в `src/model/serve.js` — стартовые значения, а не истина.
  Смещённый базовый уровень смещает всё распределение;
- модель не знает про травмы, усталость, погоду и мотивацию в конце сезона;
- `p` считается постоянной весь матч — инерция и провалы не моделируются;
- прежде чем ставить деньги, прогони бэктест на исторических котировках.
  Преимущество на бумаге и преимущество после лимитов и закрытия линии — разные вещи.

Лимиты на этом рынке низкие, линию редко двигают вручную — там и живёт
неэффективность, ради которой всё и затевалось.

## Развёртывание

Сервер слушает `0.0.0.0:8100`. Про доступ с телефона, HTTPS и настройку прокси —
`deploy/README.md`; там же готовые конфиги Caddy и скрипт диагностики.

Офлайн-режим и установка на домашний экран требуют HTTPS. По `http://` на голый IP
браузер не зарегистрирует service worker — приложение работает, но как обычный
сайт. Это ограничение платформы, приложение его обрабатывает и не падает.

## Структура

```
server.js                 HTTP-сервер: статика + /api/signals
src/model/                математика: гейм, тай-брейк, сет, матч, подача
src/odds.js               снятие маржи, преимущество, Келли
src/signals.js            связка модели с рынком
src/stats.js              справочник игроков с усадкой к среднему
src/providers/            mock и api-tennis
scripts/build-stats.js    сборка статистики из архива Сакманна
scripts/probe-provider.js диагностика ответа провайдера
scripts/generate-icons.js генерация иконок PWA
public/                   интерфейс, манифест, service worker
test/                     39 тестов
```

Тесты проверяют математику по инвариантам, а не по «золотым» числам: суммы
распределений, зеркальные симметрии при перестановке игроков и подачи, монотонность
по силе подачи, согласованность вероятности победы со счётом. Значение для гейма при
`p = 0.6` сверено независимым перебором в рациональных дробях (29889/40625).
