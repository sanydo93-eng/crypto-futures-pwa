# Сигналы: теннис и футбол

PWA с двумя моделями и разделом статистики:

- **Теннис** — распределение по точному счёту матча и первого сета;
- **Футбол** — гол в первом тайме, тотал, исход и счёт тайма;
- **Статистика** — входные данные моделей: подача и приём игроков, атака и
  оборона команд.

Модель считает вероятности, они сравниваются с коэффициентами, расхождение выше
порога показывается как сигнал.

Зависимостей нет — только Node.js 20+. Ни сборки, ни `npm install`.

```bash
npm run launch    # проверки и запуск
npm start         # запуск без проверок
npm test          # 120 тестов
```

## Запуск на боевых данных

`npm start` поднимется даже при неверном ключе, несобранном справочнике и
разъехавшемся маппинге рынков — просто не покажет ни одного сигнала, и понять
почему будет неоткуда. `npm run launch` проходит те же шаги по очереди и на
каждом говорит, что не так:

```
[1] Настройки              ключ задан, провайдер api-tennis
[2] Справочник игроков     data/player-stats.json: игроков 1843
[3] Поправка вероятностей  не подобрана, модель работает как есть
[4] Связь с провайдером    ответ получен, матчей с нужными рынками: 12
[5] Пробный разбор         разобрано матчей: 12, сигналов: 2
```

Установка одной командой — на сервере или в Termux на телефоне:

```bash
git clone https://github.com/sanydo93-eng/crypto-futures-pwa.git
cd crypto-futures-pwa
bash deploy/install.sh              # спросит ключ, соберёт данные, запустит
bash deploy/install.sh --service    # плюс автозапуск через systemd
bash deploy/install.sh --provider mock   # без ключа, на демо-данных
```

Скрипт сам проверит Node, создаст `.env` с правами 600, соберёт справочник
игроков, прогонит тесты и поднимет приложение. Ключ вводится по запросу и не
попадает ни на экран, ни в историю команд.

Вручную то же самое:

```bash
cp .env.example .env && chmod 600 .env
nano .env                  # PROVIDER=api-tennis, API_TENNIS_KEY=...
npm run launch -- --check  # только проверки
npm run launch             # проверки и запуск
```

Справочник игроков скрипт соберёт сам, если его нет. Отсутствие поправки
вероятностей — нормальный режим, а не ошибка.

Отдельно про пустой справочник: сборщик **не записывает** файл, если не собрал
ни одного игрока. Пустой файл хуже отсутствующего — он выглядит собранным, молча
делает всех игроков средними и никогда не пересобирается.

## Общая идея

Точный счёт и разметка первого тайма не берутся из API — они выводятся из
моделей. Дешёвые API коэффициентов эти рынки не отдают, а структура обоих видов
спорта позволяет посчитать их самостоятельно.

```
      статистика                коэффициенты
   игроков / команд               букмекера
          │                           │
          ▼                           │
   параметры модели                   │
  (p на подаче / λ голов)             │
          │                           │
          ▼                           ▼
    распределение          снятие маржи (девиг)
      исходов                        │
          │                           │
          └────────► сравнение ◄──────┘
                         │
                    преимущество,
                    ставка по Келли
```

## Теннис: точный счёт

1. **Подача.** Аддитивная модель Klaassen & Magnus: сила подачи одного игрока и
   сила приёма другого складываются как отклонения от среднего по туру с учётом
   покрытия.
2. **Гейм.** Замкнутая формула через сумму по счетам плюс розыгрыш «ровно».
3. **Тай-брейк.** Перебор состояний с точным учётом порядка подачи (период 4).
4. **Сет.** Динамическое программирование по счёту в геймах.
5. **Матч.** Свёртка сетов с точным учётом того, кто подаёт первым в следующем.

Пространство состояний крошечное, поэтому всё считается перебором точно —
Монте-Карло не нужно, результат детерминирован.

### Что видно только в такой модели

Счета, где фаворит закрывает сет на своей подаче, заметно вероятнее соседних.
Для игрока с `p = 0.685` против `p = 0.59`:

| счёт 1-го сета | вероятность | последний гейм |
|---|---|---|
| 6-3 | 29.7% | фаворит держит подачу |
| 6-2 | 9.2% | нужен брейк |
| 6-1 | 11.1% | фаворит держит подачу |
| 6-4 | 8.9% | нужен брейк |

Пилообразность — следствие правил, а не артефакт. Модели, оценивающие счёт «на
глазок» от вероятности победы, этот эффект теряют целиком.

## Футбол: гол в первом тайме

Пуассоновская модель с поправкой Диксона — Коулза.

**Первый тайм считается по собственным данным первых таймов**, а не как доля от
матча. Это принципиально: до перерыва забивают примерно 45% голов, а не половину,
и «делить пополам» — значит промахнуться на несколько процентов на самом ходовом
рынке.

Поправка Диксона — Коулза корректирует известную беду независимого Пуассона: он
занижает 0:0 и 1:1 и завышает 1:0 и 0:1. Для первого тайма это ровно те счета,
из которых состоит почти весь рынок, поэтому без поправки модель смещена именно
там, где считает.

Рынки на выходе: гол да/нет, тотал 1.5, исход тайма, точный счёт тайма.

## Предпросмотр матча

Нажатие на карточку открывает разбор: параметры модели, а под ними — **все**
исходы рынка, включая невыгодные, парами полос «модель против рынка».
Смысл именно в полной картине: сигнал показывает, где расхождение перешло порог,
а предпросмотр — как модель и рынок расходятся вообще, и не выглядит ли это
расхождение случайным выбросом на одном исходе.

Полосы рынка нарисованы уже без маржи, иначе они всегда были бы выше модельных.
Окно закрывается по Esc, по кнопке и по нажатию на подложку; карточки открываются
и с клавиатуры.

## Статистика

Раздел показывает входные данные моделей — то, из чего берутся вероятности:

- **игроки** — доля выигранных очков на подаче и на приёме, размер выборки;
- **команды** — доля матчей с голом в первом тайме, голы за тайм, число матчей.

У игроков и команд с малой выборкой оценка стягивается к среднему по туру или
лиге. Наблюдаемые 72% подачи по пяти матчам — это шум, и без усадки модель
уверенно выдаёт мусорные сигналы. В таблице показаны сырые наблюдения вместе с
размером выборки, чтобы было видно, чему верить.

Пока справочники не собраны, раздел работает на демо-данных: для футбола
строится детерминированная синтетическая история, для тенниса показываются
участники ближайших матчей.

### Футбол

```bash
node scripts/build-football-stats.js --league E0 --seasons 2324,2425
```

Архив football-data.co.uk выбран потому, что в нём есть колонки `HTHG`/`HTAG` —
голы к перерыву. Без них первый тайм пришлось бы оценивать долей от матча.

Коды лиг: `E0` АПЛ, `E1` Чемпионшип, `SP1` Ла Лига, `I1` Серия A, `D1`

### Коэффициенты

```bash
cp .env.example .env && chmod 600 .env
```

Теннис — api-tennis, футбол — BetsAPI:

```bash
PROVIDER=api-tennis FOOTBALL_PROVIDER=betsapi npm start
```

Дешёвые API коэффициентов (The Odds API и аналоги) точный счёт и разметку первого
тайма не отдают — там только победитель, фора и тотал матча. Поэтому BetsAPI:
у него эти рынки есть.

**Обе схемы ответа нужно проверить перед боевым использованием.** Разбор написан
по документации и на живых ключах не проверялся. Названия рынков у букмекеров
меняются, а разъехавшийся маппинг не падает с ошибкой — он молча даёт неверные
сигналы:

```bash
npm run probe                              # теннис
npm run probe -- --sport football --raw    # футбол, с сырым ответом API
```

Скрипт печатает сырой ответ, список всех рынков в нём и то, какие из них удалось
разобрать. Если нужного рынка нет среди найденных — поправь `MARKET_MATCHERS` в
`src/providers/football/betsapi.js` или `MARKET_ALIASES` в
`src/providers/tennis/apiTennis.js`.

#### Что именно берётся из BetsAPI

| Рынок BetsAPI | Внутреннее имя |
|---|---|
| First Half Goals, линия 0.5 | `firstHalfGoal` (гол да/нет) |
| First Half Goals, линия 1.5 | `firstHalfTotal15` |
| Half Time Result | `firstHalfResult` |
| Half Time Correct Score | `firstHalfScore` |

Два места, где такая интеграция обычно ломается молча, разобраны отдельно:

- **Формат коэффициента.** Bet365 отдаёт дробь (`6/4`), иногда десятичное число,
  а равные шансы — словом `EVS`. Всё это приводится к десятичному виду, мусор
  отбраковывается, а не превращается в число.
- **Колонки точного счёта.** В колонке «2» счета записаны со стороны гостей:
  `1-0` там означает 0:1. Такие счета переворачиваются. Если у твоего букмекера
  это не так, отключается флагом `swapAwayColumn`.

#### Названия команд

Букмекер пишет «Man Utd», архив результатов — «Man United». Без сведения названий
команда не находится в справочнике, модель подставляет средний уровень лиги, и
преимущества на таком матче не будет никогда.

Сведение делает `src/football/names.js`: нормализация написания плюс словарь
сокращений. Список заведомо неполный — недостающие пары показывает `npm run probe`
строками `НЕ НАЙДЕНА В СПРАВОЧНИКЕ`, дописывать в `ALIASES`.

Обязательно задай `BETSAPI_LEAGUES`: BetsAPI отдаёт все лиги мира, а справочник
команд собирается по одной, и без фильтра почти все матчи посчитаются средними.

## Настройки

Всё через переменные окружения, см. `.env.example`:

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `PORT` / `HOST` | `8100` / `0.0.0.0` | `0.0.0.0` обязателен для доступа с телефона |
| `PROVIDER` | `mock` | `mock` или `api-tennis` |
| `FOOTBALL_PROVIDER` | `mock` | `mock` или `betsapi` |
| `BETSAPI_LEAGUES` | — | Фильтр лиг по подстроке, через запятую |
| `BETSAPI_MAX_EVENTS` | `40` | Потолок матчей за обновление |
| `MIN_EDGE` | `0.05` | Порог преимущества для сигнала |
| `MIN_PROBABILITY` | `0.02` | Отсечка редких исходов |
| `DEVIG_METHOD` | `power` | Способ снятия маржи |
| `KELLY_FRACTION` | `0.25` | Доля от полного критерия Келли |
| `TENNIS_CALIBRATION_PATH` | `data/tennis-calibration.json` | Поправка вероятностей от бэктеста |

Хостам, к которым приложение ходит наружу, нужен доступ с сервера:
`api.api-tennis.com` и `api.b365api.com` за котировками,
`raw.githubusercontent.com` и `www.football-data.co.uk` за архивами статистики.

Про `DEVIG_METHOD`: `power` подбирает показатель `k` в `p = (1/кэф)^k`, что
учитывает переоценку аутсайдеров. На рынках с десятком исходов это заметно
точнее пропорционального деления, которое размазывает маржу поровну.

## Бэктест

```bash
npm run backtest -- --tour atp --from 2021 --to 2025
npm run backtest -- --tour wta --surface clay --half-life-days 200
npm run backtest -- --file data/atp_2024.csv     # повторный прогон без загрузки
```

**Что он проверяет и что нет.** Проверяет калибровку: случаются ли заявленные
70% именно в 70% случаев и совпадает ли предсказанное распределение по счетам с
наблюдаемым. Прибыльность не проверяет — исторических котировок на точный счёт
в открытом доступе нет.

Это не отговорка, а порядок действий. Плохо откалиброванная модель проиграет
гарантированно; хорошо откалиброванная — всего лишь может выиграть. Первое
проверяется бесплатно и прямо сейчас, второе требует архива котировок.

Прогон идёт строго по времени: матч прогнозируется по данным, известным **до**
него, и только потом попадает в статистику. Заглядывание вперёд — главный способ
получить прекрасные и полностью фиктивные метрики, поэтому:

- статистика игрока копится инкрементально, вес старых матчей убывает
  экспоненциально (`--half-life-days`, по умолчанию год);
- базовые уровни подачи считаются по разогревочной части выборки, а не по всей;
- игрок A выбирается по алфавиту, а не «победитель первым» — иначе A побеждает
  всегда и калибровка вырождается;
- кто подавал первым, в архиве не записано, поэтому берётся смесь двух вариантов
  в равных долях.

### Как читать отчёт

```
  Брайер:            0.1562   (монетка: 0.2500)
  Навык над базой:   25.7%
  Ошибка калибровки: 3.2%

    прогноз      обещано   случилось   матчей   расхождение
    60.0%-70.0%      65.7%       69.4%      183    +3.7%
    80.0%-90.0%      85.2%       80.7%      187    -4.5%
```

- Брайер заметно ниже 0.25 и навык выше нуля — модель несёт информацию.
- **Ошибка калибровки — главное число.** Выше 3-4% означает, что на точном счёте
  маржа съест модель раньше, чем та что-то заработает.
- В таблицах счетов важно совпадение колонок «предсказано» и «наблюдалось»
  по каждой строке отдельно, а не в сумме: именно там видно, есть ли в
  реальности та пилообразность по счетам, которую обещает модель.

### Поправка вероятностей

Параметры модели оцениваются по конечной выборке, значит с шумом, а шум
систематически стягивает прогнозы к середине: модель говорит 75%, случается 78%.
Это лечится не улучшением модели, а отдельным слоем поправки:

- **шкалирование Платта** для победы в матче: `p -> sigmoid(a·logit(p) + b)`;
- **температура** для распределения по счетам: `p^(1/T)` с перенормировкой.

Обе подбираются на первой половине выборки и проверяются на второй:

```bash
npm run backtest -- --tour atp --from 2021 --to 2025 \
  --save-calibration data/tennis-calibration.json
```

**Поправка не сохраняется, если на проверочной половине она не улучшила прогноз.**
Это не перестраховка: если расхождение на обучающей половине было шумом, а не
смещением, поправка выучит именно шум и на новых матчах сделает хуже. Отчёт
показывает обе колонки — «было» и «стало», решение принимается по лог-потере
как строгому правилу оценки. Перебить отказ можно флагом `--force-calibration`,
но это почти всегда ошибка.

Сохранённый файл подхватывается боевым расчётом через `TENNIS_CALIBRATION_PATH`
и применяется **до** сравнения с рынком — иначе преимущество считалось бы по
непоправленным числам.

### Что нужно для проверки деньгами

Архив котировок с привязкой к матчам. Варианты по возрастанию затрат:

1. **Собирать самому.** Включить провайдер и складывать ответы в лог — через
   пару месяцев появится собственный архив с закрытием линии. Самый дешёвый путь
   и единственный, дающий цены, по которым ты реально мог поставить.
2. **tennis-data.co.uk** — бесплатный архив с котировками, но только на
   победителя матча. Точного счёта там нет. Как проверка вменяемости годится:
   если модель не бьёт закрытие на победителе, на точном счёте ей делать нечего.
3. **Платный архив BetsAPI** — там есть история по экзотическим рынкам.

## Трезво про ожидания

Маржа на точном счёте — 15–25% против 2–5% на победителе матча. Это значит:

- модель должна быть **откалибрована**, а не просто «часто угадывать»;
- базовые уровни в `src/tennis/serve.js` — стартовые значения, а не истина;
  смещённый базовый уровень смещает всё распределение;
- модели не знают про травмы, усталость, погоду, мотивацию и составы;
- в теннисе `p` постоянна весь матч, в футболе λ постоянна весь тайм — инерция
  и удаления не моделируются;
- прежде чем ставить деньги, прогони бэктест на исторических котировках.
  Преимущество на бумаге и преимущество после лимитов и закрытия линии —
  разные вещи.

Лимиты на этих рынках низкие, линию редко двигают вручную — там и живёт
неэффективность, ради которой всё затевалось.

## Развёртывание

- `deploy/termux.md` — установка с телефона через Termux, в том числе запуск
  приложения прямо на телефоне (там `localhost` даёт защищённый контекст, и
  офлайн с иконкой на экране работают без домена и HTTPS);
- `deploy/README.md` — доступ снаружи, firewall, HTTPS, конфиги Caddy;
- `deploy/signals.service` — юнит systemd;
- `deploy/doctor.sh` — сбор диагностики одной командой, когда что-то не работает;
- `deploy/expose.sh` — открыть доступ снаружи: firewall, проверка, при `--port80` перевод на порт 80;
- `deploy/diagnose.sh` — диагностика недоступности порта.

Тесты проверяют математику по инвариантам, а не по «золотым» числам: суммы
распределений, зеркальные симметрии при перестановке игроков и подачи,
монотонность, согласованность вероятности победы со счётом, эквивалентность
поправки Диксона — Коулза независимому Пуассону при `rho = 0`. Значение для гейма
при `p = 0.6` сверено независимым перебором в рациональных дробях (29889/40625),
средние по лиге — на выборке, считаемой руками.

Разбор ответа BetsAPI покрыт тестами на фикстуре, воссозданной по документации.
Они доказывают, что маппинг внутренне согласован и устойчив к неполным данным —
но не то, что схема совпадает с реальной. Это проверяется только `npm run probe`
на живом токене.
